Spec-driven development

Structured specs instead of walls of Markdown.

Spec-driven workflows have agents write requirements, plans and task lists as pages of prose. It reads well, but it is long, nothing checks it, and reviewers end up skimming. In archspec the design is data, so it can be validated, diffed line by line, drawn as diagrams and sliced into exactly what one agent needs.

  1. Draft

    You or your agent write the YAML. Start with the business flow and add detail only where it matters.

  2. Check and review

    The checker reports mistakes with line numbers. Reviewers read the diagrams and the diff, and record decisions in the spec.

  3. Build

    Hand each agent the brief for its step: what it receives, what it writes, what it sends and how it handles errors.

  4. Keep in sync

    The spec stays next to the code. CI checks it on every pull request, so the design and the build don't drift apart.

What changes when the design is a spec.

01

Start with the business, then drill down.

Begin with people and systems, in words a business stakeholder recognises. Open a system to see the services, queues and databases inside it; open a service to see its endpoints and what it owns. Every level comes from the same file, so they never disagree.

  • One diagram per level, drawn for you
  • Lines roll up: one arrow between systems stands for every connection inside
  • Links with no design under them yet are flagged, so you see what is left to do
  • Go as deep as you need: stop at a business sketch, map the components, or specify every endpoint and payload

Why

A picture can't be wrong. A spec can.

Visio, draw.io and Mermaid draw pictures, and design docs describe them in prose. You can't drill from the business view into a service's contract, and the drawing won't notice that card numbers cross the internet unencrypted, that two services write the same database, or that a timeout is shorter than the calls behind it. Those mistakes turn up in code review, in testing or in production.

archspec treats the design as code. One file says who uses which systems, what runs inside them, how they connect, what data moves and in which order. Because it is precise, it can be checked, and every view is generated from it, so the diagrams never drift from the spec.

What you get from one file

Every view your reviewers need, generated and kept in sync.

Checks like a static analyzer

{{rule_count}} rules type-check field mappings and catch unencrypted personal data, dual writes, missing timeouts, synchronous call cycles, unowned database access and untested steps, each with the line to fix.

Diagrams you can edit

Architecture and sequence diagrams drawn natively, with a legend. Add boxes, connections and steps on the diagram: archspec writes them into the YAML and keeps your comments.

Business view first

Start with people and systems joined by plain-language links. Open a system to design its services, queues and databases; open a service to see its endpoints and payloads.

Security review built in

A ports-and-protocols matrix with direction, encryption, auth and the sensitivity of the data on every connection (PII, PCI, PHI), and a table of every trust-boundary crossing.

API reference and OpenAPI

A Swagger-style reference for any box: endpoints, payloads, responses, errors, message handlers and the calls it makes. Download OpenAPI 3.1 for each service.

Briefs for coding agents

Slice the spec into the exact brief a developer or coding agent needs to build one step: the payloads, mappings, tables and error handling, and nothing else.

Reviews live in the spec

Mark a finding reviewed, or done with a comment. The review is written into the file, so it is versioned and discussed in the same pull request as the design.

Exports

SVG and PNG diagrams, Markdown and CSV security tables, Postgres DDL, Mermaid, LikeC4 and a design doc. The spec itself is plain YAML you keep next to the code.

Private by design

Your architecture never leaves your machine.

The playground is a single page with the engine, the rule pack and the guide built in. After it loads it makes no network requests at all, and a Content-Security-Policy that blocks every outbound connection makes the browser hold it to that.

  • No account, no server, no analytics
  • Work is kept in your browser between visits
  • Open and save .spec.yaml files on your own computer
  • Keeps working offline once loaded

In your pipeline

The same engine checks every pull request.

Keep specs next to the code. The command line checks them in CI with text, JSON or SARIF output, so findings appear as annotations on the pull request, and renders every diagram and table for your docs.
